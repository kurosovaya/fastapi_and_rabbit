# ТЗ: Webhook Delivery Service

Портфельный проект. Асинхронный сервис доставки вебхуков с гарантиями at-least-once, ретраями, DLQ и полноценным нагрузочным контуром.

**Версия:** 1.0
**Стек:** Python 3.12+, FastAPI, RabbitMQ (aio-pika), MongoDB (motor), Locust, Prometheus, Grafana, Docker Compose

---

## 1. Цель проекта

Построить и **измерить** систему асинхронной доставки HTTP-вебхуков внешним подписчикам в условиях, когда подписчики ненадёжны: отвечают ошибками, таймаутят, лежат.

Проект имеет два равнозначных результата:

1. **Работающий сервис** с явно сформулированными и проверенными гарантиями доставки.
2. **Отчёт о нагрузочном тестировании** (`PERFORMANCE.md`), содержащий гипотезы, эксперименты, графики и выводы.

Второй результат важнее первого. Код без измерений - это учебный CRUD; измерения с выводами - это инженерная работа.

### 1.1. Что проект должен демонстрировать

- Проектирование гарантий доставки в распределённой системе (dual write, идемпотентность, at-least-once)
- Владение RabbitMQ на уровне топологии, а не "подключил библиотеку"
- Осознанную работу с MongoDB: атомарность документа, индексы, ограничения модели
- Перф-инженерию: постановку эксперимента, снятие корректных метрик, интерпретацию результата
- Понимание методологических ловушек нагрузочного тестирования

## 2. Глоссарий

| Термин | Значение |
|---|---|
| **Event** | Событие в системе-источнике, подлежащее рассылке. Создаётся через API. |
| **Subscription** | Подписка внешнего клиента на определённые типы событий. Содержит URL и секрет. |
| **Delivery** | Единица работы: доставка конкретного события конкретной подписке. |
| **Attempt** | Одна HTTP-попытка в рамках Delivery. |
| **Sink** | Тестовый сервис-эмулятор клиентского endpoint с управляемым поведением. |
| **DLQ** | Dead Letter Queue - очередь окончательно неуспешных доставок. |
| **Lease** | Временное владение задачей воркером. |
| **E2E latency** | Время от приёма события API до фактической доставки в sink. |

### 3.1. Сервисы

| Сервис | Ответственность |
|---|---|
| `api` | Приём событий и управление подписками. Быстрый ответ, никакой доставки. |
| `worker` | Потребление из очереди, HTTP-доставка, ретраи, запись результата. Масштабируется горизонтально. |
| `sink` | Эмулятор клиентских endpoint с управляемой задержкой и процентом ошибок. **Обязательный компонент** - без него нагрузочный тест измеряет localhost, а не реальность. |
| `mongo` | Хранилище событий, подписок, доставок. Single-node replica set. |
| `rabbitmq` | Брокер. Management plugin включён для снятия метрик. |
| `prometheus` + `grafana` | Наблюдаемость. |

> **Внимание:** MongoDB должна быть поднята как **single-node replica set** (`rs.initiate()` в init-скрипте), иначе многодокументные транзакции недоступны. На голом `mongod` они не работают.

## 4. Функциональные требования

### 4.1. `POST /subscriptions`

Регистрация подписки.

**Request**
```json
{
  "url": "http://sink:8080/hook/client-42",
  "event_types": ["order.created", "payment.succeeded"],
  "secret": "whsec_..."
}
```

**Response `201`**
```json
{ "id": "sub_01H...", "url": "...", "event_types": [...], "created_at": "..." }
```

**Требования**
- Валидация URL (схема, хост)
- `secret` хранится, но никогда не возвращается в ответах
- Минимум: в `README` описать риск SSRF (клиент регистрирует `http://169.254.169.254/`) и выбранную стратегию

---

### 4.2. `POST /events`

Приём события. **Ключевой endpoint по производительности.**

**Headers**
- `Idempotency-Key: <uuid>` - обязательный

**Request**
```json
{ "event_type": "order.created", "payload": { "order_id": 12345 } }
```

**Response `202`**
```json
{ "event_id": "evt_01H...", "accepted_at": "...", "subscriptions_matched": 3 }
```

**Требования**
- Ответ **не должен** ждать доставки
- Целевой p99 < 50 мс при нагрузке до точки насыщения
- Повторный запрос с тем же `Idempotency-Key` возвращает **исходный** ответ и **не** создаёт второе событие
- Fan-out: доставка создаётся для каждой подписки, у которой `event_type` попадает в список

---

### 4.3. `GET /events/{event_id}`

Статус события и всех его доставок.

**Response `200`**
```json
{
  "event_id": "evt_01H...",
  "event_type": "order.created",
  "created_at": "...",
  "deliveries": [
    {
      "subscription_id": "sub_01H...",
      "status": "delivered",
      "attempts": 2,
      "last_error": "500 Internal Server Error",
      "delivered_at": "...",
      "e2e_latency_ms": 1843
    }
  ]
}
```

---

### 4.4. `POST /deliveries/{delivery_id}/retry`

Ручной ретрай доставки из DLQ. Возвращает `202`.

---

### 4.5. `GET /metrics`

Prometheus-формат. Реализуется во всех трёх сервисах (`api`, `worker`, `sink`).

---

### 4.6. Sink API (тестовый эмулятор)

| Endpoint | Назначение |
|---|---|
| `POST /hook/{client_id}` | Приём вебхука. Поведение определяется профилем клиента. |
| `PUT /config/{client_id}` | Настройка профиля: `{delay_ms, error_rate, timeout_rate}` |
| `GET /received` | Счётчики принятого - для проверки потерь и дублей |
| `POST /reset` | Сброс состояния между прогонами |

Sink обязан **проверять HMAC-подпись** и отвечать `401` при несовпадении. Это единственный автоматический контроль корректности подписи.

## 5. Требования к доставке

### 5.1. Подпись

```
X-Signature: sha256=<hex(HMAC-SHA256(secret, raw_body))>
X-Event-Id: evt_01H...
X-Delivery-Id: dlv_01H...
X-Attempt: 2
```

Подпись считается по **сырому телу** запроса, не по пересериализованному словарю.

### 5.2. Retry ladder

| Попытка | Задержка перед ней |
|---|---|
| 1 | 0 |
| 2 | 1 s |
| 3 | 5 s |
| 4 | 25 s |
| 5 | 125 s |
| после 5 | → DLQ, статус `failed` |

**Обязательно:** полный jitter на каждой ступени (`delay * random()`), иначе при массовом отказе подписчика все ретраи придут одной волной (thundering herd).

### 5.3. Классификация ответов

| Ответ подписчика | Действие |
|---|---|
| `2xx` | `delivered`, финал |
| `4xx` (кроме `408`, `429`) | `failed` немедленно, **без ретраев** - клиент не починится сам |
| `408`, `429`, `5xx` | ретрай по лестнице |
| Таймаут / connection error | ретрай по лестнице |

Различение "не буду ретраить" и "буду" - обязательное требование. Ретраить `400 Bad Request` пять раз бессмысленно.

### 5.4. Таймауты

Явные таймауты на исходящий запрос: `connect` и `read` раздельно. Значения - через переменные окружения.

Клиент `httpx.AsyncClient` **создаётся один раз на жизнь воркера** и переиспользуется. Создание клиента на каждый запрос - красный флаг: теряется пул соединений и keep-alive.

## 6. Модель данных (MongoDB)

### 6.1. `subscriptions`

```javascript
{
  _id: "sub_01H...",
  url: "http://sink:8080/hook/client-42",
  event_types: ["order.created", "payment.succeeded"],
  secret: "whsec_...",
  active: true,
  created_at: ISODate()
}
```

**Индексы**
```javascript
db.subscriptions.createIndex({ event_types: 1, active: 1 })
```

### 6.2. `events`

```javascript
{
  _id: "evt_01H...",
  idempotency_key: "550e8400-...",
  event_type: "order.created",
  payload: { ... },
  created_at: ISODate(),
  published: false            // для outbox-релеера
}
```

**Индексы**
```javascript
db.events.createIndex({ idempotency_key: 1 }, { unique: true })
db.events.createIndex({ published: 1, created_at: 1 })   // для outbox-поллера
db.events.createIndex({ created_at: 1 }, { expireAfterSeconds: 604800 })  // TTL 7 дней
```

Уникальный индекс по `idempotency_key` - **основной механизм идемпотентности**. Реализация через `insert_one` + перехват `DuplicateKeyError`, а не через `find_one` с последующим `insert_one` (последнее - гонка).

### 6.3. `deliveries`

```javascript
{
  _id: "dlv_01H...",
  event_id: "evt_01H...",
  subscription_id: "sub_01H...",
  status: "pending",          // pending | in_progress | delivered | failed
  attempt: 0,
  attempt_epoch: 0,           // fencing token
  locked_by: null,
  locked_until: null,
  next_attempt_at: ISODate(),
  last_error: null,
  accepted_at: ISODate(),     // время приёма события - база для E2E latency
  delivered_at: null
}
```

**Индексы**
```javascript
db.deliveries.createIndex({ event_id: 1 })
db.deliveries.createIndex({ status: 1, locked_until: 1 })   // reclaim зависших
db.deliveries.createIndex({ event_id: 1, subscription_id: 1 }, { unique: true })
```

### 6.4. Решение по вложенности

Доставки вынесены **в отдельную коллекцию**, а не вложены массивом в `events`.

Обоснование (должно быть в `README`): при большом количестве подписчиков вложенный массив упирается в лимит документа 16 МБ, и каждое обновление статуса одной доставки переписывает документ целиком. Вложение допустимо только при гарантированно малом fan-out.

## 7. Топология RabbitMQ

### 7.1. Exchange и очереди

```
webhooks.direct (direct exchange, durable)
  │
  ├─ routing_key "deliver"    → q.deliveries        (quorum, durable)
  │                                 │ nack(requeue=false)
  │                                 ▼
  │                              webhooks.retry (direct)
  │
  ├─ routing_key "retry.1"    → q.retry.1s     (TTL 1000 ms,   DLX → webhooks.direct/deliver)
  ├─ routing_key "retry.2"    → q.retry.5s     (TTL 5000 ms,   DLX → webhooks.direct/deliver)
  ├─ routing_key "retry.3"    → q.retry.25s    (TTL 25000 ms,  DLX → webhooks.direct/deliver)
  ├─ routing_key "retry.4"    → q.retry.125s   (TTL 125000 ms, DLX → webhooks.direct/deliver)
  │
  └─ routing_key "dead"       → q.dlq          (без TTL, ручной разбор)
```

### 7.2. Почему лестница очередей, а не одна очередь с TTL

**Это ключевое архитектурное решение проекта, его нужно уметь защитить.**

В RabbitMQ per-queue TTL применяется **только к головному сообщению очереди**. Если в общей retry-очереди впереди лежит сообщение с оставшимся временем 120 с, все сообщения за ним ждут его истечения независимо от собственного TTL - классический head-of-line blocking.

Отсюда: отдельная очередь на каждую ступень задержки, внутри одной очереди все сообщения имеют одинаковый TTL, порядок соблюдается естественно.

Альтернатива - плагин `rabbitmq_delayed_message_exchange`. Не входит в стандартную поставку и несовместим с quorum-очередями. В `README` следует упомянуть как рассмотренный и отклонённый вариант с обоснованием.

### 7.3. Обязательные настройки

| Настройка | Значение | Почему |
|---|---|---|
| `publisher_confirms` | `True` | Без них `publish()` ничего не гарантирует |
| `mandatory` | `True` | Ловить случай, когда сообщение никуда не сроутилось |
| `delivery_mode` | `PERSISTENT` | Иначе сообщения теряются при рестарте брокера |
| Тип очередей | `quorum` | Реплицируемость, корректный `x-delivery-count` |
| `prefetch_count` | конфигурируемый | **Главная ручка** для экспериментов части 9 |
| ack | ручной, после успеха | `no_ack=True` = потеря при падении воркера |
| При неуспехе | `nack(requeue=False)` | `requeue=True` создаёт бесконечный цикл poison message |

## 8. Гарантии и инварианты

### 8.1. Заявленная гарантия

**At-least-once.** Exactly-once по сети недостижим; система обязана это явно декларировать в `README` и переложить дедупликацию на получателя через `X-Event-Id` + `X-Delivery-Id`.

### 8.2. Инварианты, подлежащие проверке

| # | Инвариант |
|---|---|
| I1 | Событие, принятое с `202`, будет доставлено или помечено `failed`. Тихой потери не существует. |
| I2 | Пара `(event_id, subscription_id)` существует в единственном экземпляре (уникальный индекс). |
| I3 | Два воркера не обрабатывают одну доставку **результативно** одновременно. |
| I4 | Повторный `Idempotency-Key` не создаёт второго события. |
| I5 | Убийство воркера в любой момент не приводит к потере сообщения. |

### 8.3. Dual write

`POST /events` должен записать событие в Mongo **и** опубликовать в RabbitMQ. Между операциями сервис может упасть.

**Требуется выбрать и обосновать один из подходов:**

- **A. Transactional outbox.** Запись в Mongo с `published: false`, отдельный релеер (поллер или Change Stream) публикует в Rabbit и проставляет флаг. Надёжно, добавляет задержку и компонент.
- **B. Publish-then-persist с компенсацией.** Быстрее, требует reconciliation-процесса.

Вариант "два `await` подряд без обработки промежуточного отказа" - неприемлем.

### 8.4. Fencing token

Lease (`locked_until`) **не является мьютексом**. Сценарий отказа: воркер не умер, а затормозил (GC-пауза, своп, дросселирование CPU в контейнере); lease истёк; задачу забрал второй воркер; первый очнулся и записал свой результат.

**Решение:** монотонный `attempt_epoch`. При захвате задачи он инкрементируется. Запись результата - условная:

```python
await db.deliveries.update_one(
    {"_id": delivery_id, "locked_by": worker_id, "attempt_epoch": my_epoch},
    {"$set": {"status": "delivered", "delivered_at": now}},
)
# matched_count == 0 → мой lease протух, результат отбрасывается
```

Увеличение времени lease проблему **не решает**, только снижает вероятность.

## 9. Нефункциональные требования

### 9.1. SLO

| Метрика | Цель |
|---|---|
| `POST /events` p99 | < 50 мс до точки насыщения |
| E2E p95 (здоровый подписчик) | < 2 с |
| Потери сообщений при `docker kill` воркера | 0 |
| Горизонтальное масштабирование | throughput растёт не менее чем на 70% от линейного при 1→4 воркерах |

### 9.2. Обязательные метрики Prometheus

**api**
- `http_request_duration_seconds{endpoint}` - histogram
- `events_accepted_total`
- `events_idempotent_hits_total`
- `publish_failures_total`

**worker**
- `delivery_attempts_total{result}` - `delivered` / `retry` / `failed`
- `delivery_duration_seconds` - histogram, время HTTP-запроса к подписчику
- `e2e_latency_seconds` - **histogram, ключевая метрика**: `delivered_at - accepted_at`
- `worker_inflight` - gauge, текущая конкурентность
- `redeliveries_total`

**RabbitMQ** (через exporter или management API)
- `queue_messages_ready{queue}` - глубина очереди
- `queue_messages_unacknowledged{queue}`
- `queue_message_publish_rate`, `queue_message_deliver_rate`

### 9.3. Grafana

Один преднастроенный дашборд (provisioning, не ручная сборка) с четырьмя обязательными панелями:

1. **Queue depth во времени** - самый информативный график проекта
2. **E2E latency** - p50 / p95 / p99
3. **Throughput**: accepted rate vs delivered rate на одних осях
4. **Unacked messages** + количество воркеров

## 10. Нагрузочное тестирование

### 10.1. Что измерять и что не измерять

**Не является целевой метрикой:** p99 на `POST /events`. Он измеряет скорость записи в очередь и остаётся низким даже когда система полностью не справляется с доставкой.

**Целевая метрика:** E2E latency и производная от неё - **сходимость очереди**. Если `queue depth` при постоянной нагрузке не возвращается к нулю, система не медленная, а **несходящаяся**: отставание растёт неограниченно.

### 10.2. Locust: структура

```
locust/
  locustfile.py          # PublisherUser
  shapes/
    step_load.py         # ступенчатая нагрузка - эксперимент 1
    constant.py          # ровное плато - эксперименты 2-5
  scenarios/
    seed_subscriptions.py  # подготовка подписок и профилей sink
```

`PublisherUser` льёт `POST /events` с реалистичным распределением `event_type` и уникальным `Idempotency-Key` на запрос.

### 10.3. Обязательные эксперименты

Каждый оформляется в `PERFORMANCE.md` по шаблону:
**Гипотеза → Конфигурация → Метод → График → Наблюдение → Вывод**

---

#### Эксперимент 1. Точка насыщения

**Конфигурация:** sink - 20 мс задержки, 0% ошибок. 2 воркера, `prefetch=50`.
**Метод:** ступени 50 → 100 → 200 → 400 → 800 RPS, по 2 минуты каждая, между ступенями - пауза до опустошения очереди.
**Искомое:** RPS, при котором `queue depth` перестаёт возвращаться к нулю.
**Вывод:** ёмкость системы в текущей конфигурации.

---

#### Эксперимент 2. Влияние prefetch

**Конфигурация:** фиксированная нагрузка на 70% от найденной ёмкости. `prefetch_count` = 1, 10, 50, 200, 1000.
**Снимать:** throughput (msg/s), E2E p99, `worker_inflight`, память воркера.
**Ожидаемая форма:** throughput растёт и выходит на плато; E2E latency начинает расти **раньше**, чем throughput достигает плато.
**Вывод:** обосновать выбранное значение. Объяснить связь оптимума с временем ответа sink.

---

#### Эксперимент 3. Медленный подписчик (head-of-line blocking)

**Конфигурация:** 5% подписчиков настроены на задержку 10 с. Остальные 95% - 20 мс.
**Метод:** прогон "до", фикс, прогон "после".
**Ожидаемое "до":** деградация E2E latency у **всех** подписчиков, включая здоровых.
**Фикс - выбрать и обосновать:**
- Ограничение конкурентности на подписку (семафор по `subscription_id`)
- Отдельная очередь и пул воркеров для "медленных"
- Circuit breaker на подписку

**Вывод:** графики до/после на одних осях, с числами.

---

#### Эксперимент 4. Отказы

Три сценария под нагрузкой 50% от ёмкости:

| Сценарий | Что проверяется |
|---|---|
| `docker kill worker` | Потери = 0. Дубли - посчитать через `GET /received` на sink. |
| `docker kill rabbitmq` | Поведение API: должен явно деградировать (`503` или outbox), а не висеть до таймаута |
| `docker kill mongo` | То же |

**В отчёт:** конкретные числа потерянных и задублированных сообщений, время восстановления после подъёма компонента.

---

#### Эксперимент 5. Горизонтальное масштабирование

**Конфигурация:** 1 → 2 → 4 → 8 воркеров при фиксированной нагрузке выше ёмкости одного воркера.
**Ожидаемое:** рост throughput близко к линейному, затем выход на плато.
**Обязательно:** найти и назвать компонент, в который упёрлись при выходе на плато (Mongo? sink? один канал на всех? CPU генератора?). Ответ "не знаю" - незачёт по эксперименту.

### 10.4. Методологические требования

Раздел `PERFORMANCE.md` → "Валидность измерений" обязан покрыть:

**Coordinated omission.** Locust по умолчанию работает в closed-loop: виртуальный пользователь ждёт ответа перед следующим запросом. Когда система тормозит, генератор автоматически снижает нагрузку и **скрывает** проблему из статистики. Требуется либо использовать `constant_throughput` (open-loop), либо явно зафиксировать ограничение в отчёте.

**Изоляция генератора.** Locust и тестируемая система - разные контейнеры с явными лимитами CPU (`cpus:` в compose). Утилизация контейнера Locust мониторится и приводится в отчёте: если генератор упёрся в 100% CPU, все измеренные цифры недействительны.

**Потолок одного процесса.** Один Locust-процесс ограничен примерно одним ядром. Выше нескольких тысяч RPS - distributed-режим (master + worker'ы).

**Блокирующие вызовы под gevent.** Любая не-monkey-patched библиотека внутри task блокирует весь Locust-воркер. Проверить используемый HTTP-клиент.

**Прогрев.** Первые 30 секунд каждого прогона отбрасываются (JIT-прогрев отсутствует, но прогреваются пулы соединений, кэши Mongo, page cache).

**Воспроизводимость.** Каждый прогон - фиксированный seed, зафиксированные версии образов, `POST /reset` на sink между прогонами.
